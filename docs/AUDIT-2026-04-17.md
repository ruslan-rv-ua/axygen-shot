# Аудит проекту Axygen Shot

> **Тип задачі:** 🔧 Рефакторинг/якість + 🔒 Безпека + 🏗️ Архітектура
> **Стек:** Rust 2024, Windows Win32 API, `windows` crate v0.62
> **Дата аудиту:** 2026-04-17
> **Сфера:** повний огляд коду, архітектури, безпеки, тестування, відповідності PRD та ADR

## TL;DR

> Проект має **здорову архітектуру, високу якість коду та повне тестове покриття чистих модулів**. Головні проблеми: **невідповідність PRD/ADR у зоні console subsystem + AttachConsole** (наразі не реалізовано), **порушення принципу stateless у `watch.rs` через `static mut`**, **race condition у Restart через daemon-mutex**, **колізія імен файлів у watch mode в межах однієї секунди**, **недоекранування TOML-рядків в `--init`**, **відсутність CI-пайплайну**. Усі інші знахідки — косметичні або низькопріоритетні.

## Знайдені проблеми — за пріоритетом

### 🔴 HIGH — потрібно виправити

#### 1. Відсутня реалізація console subsystem + AttachConsole

**Файл:** немає; має бути в [src/main.rs](src/main.rs:1)
**PRD/ADR reference:** PRD L148, ADR L280-297

**Суть:** PRD і ADR явно вимагають:
```rust
#![windows_subsystem = "windows"]
// + AttachConsole(ATTACH_PARENT_PROCESS) в CLI-режимі
```

**Наслідки:**
- Запуск `shot.exe` з Provider'а/Task Scheduler/shortcut на GUI → **миготіння чорного консольного вікна** перед виконанням. Для сліпого користувача це не візуальна проблема, але для майбутніх зрячих користувачів — помилка UX.
- У watch-режимі: якщо запустити `shot --watch` з GUI-контексту, створиться консоль, яку потім ховає `DETACHED_PROCESS` — але перший процес має консоль, яка миготить.
- Наслідок для логіки `is_detached()` у [src/watch.rs:207-209](src/watch.rs#L207-L209): зараз детектор працює через `GetConsoleWindow().0.is_null()`. Для SUBSYSTEM:WINDOWS це працює інакше — без `AttachConsole` консолі немає, тому `is_detached()` помилково поверне `true` при запуску з терміналу. Поточний код покладається на те, що бінарник — console subsystem, а це суперечить ADR.

**Рекомендація:**
1. Додати в [src/main.rs:1](src/main.rs#L1): `#![windows_subsystem = "windows"]`
2. Додати hello-attach на початку `main()`:
```rust
use windows::Win32::System::Console::{AttachConsole, AllocConsole, ATTACH_PARENT_PROCESS};
fn main() {
    // Для CLI-режиму: підключитися до батьківської консолі.
    // Watch-режим перевіряє GetConsoleWindow окремо.
    unsafe {
        let _ = AttachConsole(ATTACH_PARENT_PROCESS);
    }
    // ... решта
}
```
3. Переробити `is_detached()` в `watch.rs` — замість `GetConsoleWindow` використати явний маркер (наявність `--daemon-parent-pid` OR аргумент `--detached`), бо `GetConsoleWindow` не надійний під `SUBSYSTEM:WINDOWS`.

**Рівень впевненості:** ✅ підтверджено тестуванням: код не містить цих викликів.

#### 2. `static mut` у watch.rs — порушення PRD "no global mutable state"

**Файл:** [src/watch.rs:51-52](src/watch.rs#L51-L52)

```rust
static mut DAEMON_CFG: Option<*const CaptureConfig> = None;
static mut CAPTURING: bool = false;
```

**Проблеми:**
- Прямо суперечить архітектурі PRD: "All modules are stateless — no global mutable state."
- `static mut` у Rust 2024 — сильно відмічений код-смел, Clippy warn-by-default у майбутньому. Edition 2024 вже вимагає `&raw mut` або `addr_of_mut!` у багатьох контекстах.
- Формально UB-безпечно лише тому, що daemon однопотоковий. Будь-який майбутній рефакторинг (наприклад, capture у background thread) зламає це тихо.
- `CAPTURING` — непотрібний, бо wndproc виконується строго sequentially (`GetMessage`/`DispatchMessage` блокує, `WM_HOTKEY` не може re-enter у пределах одного `DispatchMessage`). Його єдина роль — блокувати рекурсивні виклики, **яких не може бути в однопотоковому message loop**, якщо `do_capture` не робить `PeekMessage`. Тобто флаг **надлишковий**.

**Рекомендація (2 варіанти, від меншого до більшого):**

**Варіант A (мінімальний, швидкий):** Інкапсулювати через `SetWindowLongPtrW(hwnd, GWLP_USERDATA, cfg_ptr as isize)` — стандартний Win32 ідіом. Убрати обидва `static mut`. `CAPTURING` видалити як non-issue для однопотокового wndproc.

**Варіант B (правильний):** Винести стан у окремий `DaemonState` struct, зберігати його поінтер через `GWLP_USERDATA`, `wndproc` читає struct через `GetWindowLongPtrW`. Цей підхід — best practice для Win32 у Rust.

Посилання: див. [windows-rs приклад з GWLP_USERDATA](https://github.com/microsoft/windows-rs/blob/master/crates/samples/windows/create_window/src/main.rs).

#### 3. Race condition у "Restart" через Global mutex

**Файл:** [src/watch.rs:516-519, 576-615](src/watch.rs#L516-L519)

**Сценарій:**
1. Користувач клікає tray → "Restart"
2. `wndproc` викликає `restart()` → спавн нового процесу з тими самими аргументами
3. `wndproc` після `restart()` викликає `PostQuitMessage(0)`
4. **Новий процес стартує, але поточний ще тримає `Global\\axygen-shot-daemon` mutex**
5. Новий процес отримає `ERROR_ALREADY_EXISTS` від `CreateMutexW` → error exit з `WatchAlreadyRunning`
6. Старий процес після цього завершить message loop і звільнить mutex — але вже пізно

**Доказ:** [src/watch.rs:343-363](src/watch.rs#L343-L363) перевіряє `ERROR_ALREADY_EXISTS`, а mutex старого daemon'у живий до повного завершення.

**Рекомендація:**
- У `wndproc` на `ID_RESTART`: **спочатку** звільнити mutex і UnregisterHotKey (можна через окремий handoff-файл або event), **потім** спавнити. Або:
- Використати паттерн "handoff": старий процес чекає сигнал від нового перед виходом з `WaitForSingleObject` на NamedEvent.
- Простіше рішення: новий процес при запуску чекає звільнення mutex до N секунд перед тим як видати помилку (`WaitForSingleObject` on mutex із timeout).

#### 4. Колізія імен файлів у watch-режимі (same-second captures)

**Файл:** [src/storage.rs:23-30](src/storage.rs#L23-L30), виклик із watch — [src/watch.rs:528-540](src/watch.rs#L528-L540)

**Формат:** `YYYY-MM-DD_HHMMSS_<title>.png` — секундна роздільність.

**У watch-режимі:**
- `label = None` завжди
- Якщо title вікна не змінюється, два `WM_HOTKEY` в межах однієї секунди дають **однакове ім'я файлу** → другий **перезаписує перший**.

**Хоча** `do_capture` обертає операцію в `CAPTURING` flag і PRD story 62-65 описує серіалізацію, **серіалізація не гарантує різні секунди**. Реальний сценарій: user натискає hotkey двічі поспіль (2 капчури за 1.2с) → обидва в одній секунді → другий перезаписує перший.

Тест [src/storage.rs:142-148](src/storage.rs#L142-L148) перевіряє `r1.filename != r2.filename`, але лише тому що передає **різні label** ("alpha"/"beta"). Для однакових labels або None-None тест пройшов би помилково, бо залежить від швидкості системи.

**Рекомендація:**
- Додати мілісекунди або sub-second suffix: `YYYY-MM-DD_HHMMSS-mmm` (де mmm = milliseconds).
- Альтернатива: check collision → додавати `_1`, `_2` suffix.
- Оновити PRD story 40, якщо формат змінюється.

#### 5. Неповне TOML-екранування в `--init`

**Файл:** [src/config.rs:140-142](src/config.rs#L140-L142)

```rust
fn escape_toml_string(s: &str) -> String {
    s.replace('\\', "\\\\").replace('"', "\\\"")
}
```

**Проблема:** не екрануються:
- `\n`, `\r`, `\t` (TOML basic string забороняє literal control chars)
- `\0` (null byte)
- Керуючі символи `\x00..\x1F`

**Експлуатація:**
```
shot --init --process=$'evil\n[malicious]\nprocess = "other.exe"'
```
створить файл з додатковою секцією. Manual checklist 10.2 лише перевіряє лапки та дужки — цього недостатньо.

**Рекомендація:**
```rust
fn escape_toml_string(s: &str) -> String {
    let mut out = String::with_capacity(s.len());
    for c in s.chars() {
        match c {
            '\\' => out.push_str("\\\\"),
            '"' => out.push_str("\\\""),
            '\n' => out.push_str("\\n"),
            '\r' => out.push_str("\\r"),
            '\t' => out.push_str("\\t"),
            c if c.is_control() => out.push_str(&format!("\\u{:04X}", c as u32)),
            _ => out.push(c),
        }
    }
    out
}
```

Рівень ризику: низький (лише local attack при підготовленому CLI), але виправлення тривіальне.

#### 7. Round-trip PNG encode → decode у clipboard

**Файл:** [src/clipboard.rs:76-104](src/clipboard.rs#L76-L104)

`capture::capture_window` кодує BGRA → PNG. `clipboard::set_image` декодує PNG → RGBA → конвертує в BGRA. Для `ClipboardMode::Both` чи `Image` це зайва робота (сотні мс на великих зображеннях).

**Рекомендація:** повертати з `capture_window` і PNG bytes, **і** сирі BGRA пікселі (`Arc<Vec<u8>>` або окрема структура). Це спрощує clipboard і не вимагає power-of-two-fold перетворень.

Вплив: performance тільки; correctness не під загрозою.

#### 8. Overflow у `clipboard::set_image` розрахунку буфера

**Файл:** [src/clipboard.rs:93](src/clipboard.rs#L93)

```rust
let mut bgra_bottomup = vec![0u8; (width * height * 4) as usize];
```

`width` та `height` — `u32`. Для 16384×16384: `width * height * 4` = `~1.07 × 10^9` — ще вміщується в u32 (max `~4.29 × 10^9`). Але для 32768×32768: `u32` overflow → неправильний розмір → write out-of-bounds через `std::ptr::copy_nonoverlapping`.

У `capture.rs:110-113` є `checked_mul` — у clipboard.rs **ні**. Додати аналогічну перевірку.

#### 9. parse_hotkey повертає `ArgError` замість `HotkeyError`

**Файл:** [src/watch.rs:99, 113, 147](src/watch.rs#L99)

`ShotError::HotkeyError` існує, `parse_hotkey` отримує hotkey-string і валідатор hotkey — семантично це hotkey error. Через це код у stderr виглядає як:
```
code: arg-error
message: Invalid hotkey 'Win+'...
```
замість логічнішого `code: hotkey-error`.

Pipeline у `run_daemon` коректно загортає у `HotkeyError` тільки коли сама `RegisterHotKey` API fails. Parse-стадію теж слід.

## Безпекова оцінка

**Модель загроз:** locally-executed CLI tool без мережевої поверхні. Головна поверхня — TOML-конфіг у project-root (контрольований розробником) та CLI-args.

| Вектор | Оцінка | Коментар |
|---|---|---|
| Path traversal у `folder` | ✅ мітиговано | `validate_folder` перевіряє, але має false positive (див. #6) |
| TOML ін'єкція через `--init` | ⚠️ | Див. #5 — потребує фікса екранування |
| Clipboard poisoning | ✅ | Тільки write, без read — нема DoS на буфер обміну |
| Privilege escalation | ✅ | `asInvoker` (явно не вказано — рекомендовано, див. #19) |
| DoS від зловмисного target window | ⚠️ | `PrintWindow` блокує до відповіді WM_PRINT. Повна зависань — target не відповідає → message loop підвисає. Тільки локальний impact. |
| Mutex name squatting | ⚠️ низький | `Global\\axygen-shot-daemon` — будь-хто на системі може створити цей mutex першим і унеможливити запуск shot.exe. Не DoS на систему, лише на нашу утиліту. Прийнятно для MVP. |
| Temp file в `%TEMP%\shot-err-{pid}.txt` | ✅ низький | Symlink attack на Windows — нетиповий; файл створюється `std::fs::write` з truncate. Якщо зловмисник контролює `%TEMP%`, у нього вже є доступ до сесії. |

**Висновок безпеки:** прийнятно для десктопного CLI-інструменту. Рекомендовано виправити #5 та задекларувати #19.

## Якість коду — загальні спостереження

**Переваги:**
- ✅ Модульна структура точно за ADR/PRD, 1-to-1 файл-модуль
- ✅ DI-trait (`WindowEnumerator`) для тестування WindowResolver — не симуляція, а справжня DI
- ✅ Повний error enum з `.code()` і людським `.format_error_message()`
- ✅ 100%-на cliмп-чистота (`-D warnings`)
- ✅ `panic = "abort"` у обох профілях — коректно для extern "system" FFI
- ✅ Хороша гігієна `unsafe`: майже всі unsafe-блоки локалізовані та мінімальні
- ✅ Комбіноване володіння ресурсами GDI з коректним cleanup на всіх error-шляхах у `capture.rs`
- ✅ Тест-покриття: 68 unit-тестів + 6 інтеграційних (чисті модулі — майже повне покриття)

**Косметичні зауваження:**
- `src/capture.rs:107` — `..mem::zeroed()` у `BITMAPINFO` задає нульовий `bmiColors[1]`, хоча `biBitCount=32` не використовує палітру. Коректно, але `BITMAPINFO` у `windows`-крейт має `bmiColors: [RGBQUAD; 1]`, і `mem::zeroed` overkill — `BITMAPINFO::default()` дорівнює тому самому без unsafe.
- `src/clipboard.rs:89` — `debug_assert_eq` на `width/height` — якщо у release build PNG декодується з іншим розміром (програмна помилка), ми мовчки обрахуємо не той буфер. Краще замінити на `assert_eq!` або на ранній `Err`.
- Повторювані блоки `wide_string(&format!("..."))` — можна винести в `named_event(prefix, pid)` helper.
- `run_daemon` — 150 рядків: варто розбити на `setup_window()`, `setup_tray()`, `run_message_loop()`.

## Підсумок

**Проект у високому стані готовності для MVP.** Код написаний акуратно, архітектура відповідає ADR, тестове покриття чистих модулів — близьке до повного. Головні зауваження — **невідповідність PRD у зоні subsystem/AttachConsole**, **порушення принципу stateless у watch.rs** та **race condition у Restart**. Усе інше — низькопріоритетний технічний борг або косметика.

**Якщо бюджет обмежений двома годинами:** виправити #5, #4, #6, #8, #9 (всі — тривіальні фікси) + заповнити #1 (SUBSYSTEM:WINDOWS) — це закриє 80% поверхні помилок при мінімальних ризиках регресії.
